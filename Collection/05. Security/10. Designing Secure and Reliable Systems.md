# 10. Designing Secure and Reliable Systems

Security and reliability are the same discipline seen from two sides: both are about a system behaving as intended under stress, whether the stress is a failing disk or an attacker. This note covers the design principles; incident handling is in [[1. Security Fundamentals|01. Security Fundamentals]], trust in networks in [[9. Zero Trust Networks|09. Zero Trust Networks]], and the build path in [[5. Secure Coding and Supply Chain|05. Secure Coding and Supply Chain]].

## Principles at a glance

| Principle | The question it answers |
| --------- | ----------------------- |
| **Least privilege** | What is the smallest access this task needs? |
| **Understandability** | Can people reason about the system and its access rules? |
| **Resilience** | How far does a failure or attack spread? |
| **Recovery** | Can we get back to a known-good state quickly and safely? |
| **Safe deployment** | Is what reaches production exactly what we built and reviewed? |

---

# Least Privilege

Applies to humans, automation and machines, across every authentication and authorisation layer. Two ideas run through it: reject **implicit authority** for tooling, and avoid **ambient authority** (for example the ability to log in as root).

- **Zero trust networking**: network location grants nothing; access depends on user credentials plus device credentials (see [[9. Zero Trust Networks|09. Zero Trust Networks]])
- **Zero touch**: remove direct human access to production. Humans act through tooling that makes predictable, controlled changes, which needs safe APIs and multi-party approval
- **Classify access by risk**: protect public data, company data, user data and cryptographic secrets differently, and treat administrative APIs that can delete data differently from read APIs. Cover who, how tightly, read or write, and what infrastructure controls

| Class | Meaning |
| ----- | ------- |
| Public | Open to anyone in the company |
| Sensitive | Limited to groups with a business purpose |
| Highly sensitive | No permanent access |

- **Infrastructure access** (reducing logging, changing encryption requirements, direct SSH, restarting services) is high risk in every class, because it can bypass the normal controls
- Read access matters too: overly broad read permissions can cause a mass data breach

## Controls

| Control | Idea |
| ------- | ---- |
| **Small functional APIs** | One endpoint does one thing, so access can be granted per action and a reviewer knows exactly what they approve |
| **Breakglass** | Emergency access that bypasses authorisation entirely; keep it audited and monitored |
| **Auditing** | Detect misuse; depends on how granular the access decision is |
| **Multi-party authorisation** | A second person approves; prevents mistakes, deters bad actors, raises attack cost and leaves a tamper-resistant record |
| **Temporary access** | Expiring group membership or on-demand grants; reduces ambient authority and shows where access is really needed |
| **Proxies / bastions** | Fall back to a restricted, heavily logged proxy when a backend has no fine-grained controls |

- Prefer granular authorisation over broad MPA: approving an action on a small API is a precise decision
- Broad MPA still works as a breakglass for unusual actions with no workflow
- This is why admins use `sudo` over logging in as root: fewer permissions when a command goes wrong

Costs to expect: more security complexity, slower collaboration, less user productivity, more developer work. Scope and prioritise by classification to keep them down.

# Understandability

The book defines understandability as how far a person with the relevant background can accurately and confidently reason about the system's **operational behaviour** and its **invariants**, including security and availability. A system may be easy to reason about under high load yet hard to reason about under crafted, malicious input.

Why it pays off:
- Fewer vulnerabilities and resilience failures: an engineer who misunderstands existing behaviour, or misses a hidden or undocumented requirement, breaks something when they change it
- Faster incident response: responders must assess damage, contain and find root causes quickly
- More confidence in security claims, which are stated as invariants

How to get it:
- Analyse the system through **invariants and mental models**
- A **layered architecture** using standardised frameworks for identity, authorisation and access control
- Clear **security boundaries**
- Software design that uses application frameworks and well-specified APIs, so security and reliability properties can be reasoned about at the framework level

# Resilience

Build resilience from layers that are each independently resilient (defence in depth).

- **Differentiate the cost of failures**: decide which features must survive any load and which can be throttled or disabled. Measure by computing resources, user experience and speed of mitigation
- **Controlled degradation**: load shedding, throttling, automated response. A severely degraded service beats an unavailable one
- **Automate responsibly**, and leave a foothold for humans

## Fail safe versus fail secure

| Choice | Behaviour | If the ACL file fails to load |
| ------ | --------- | ----------------------------- |
| **Fail open** (optimise reliability) | Keep serving what it can | Default is allow all |
| **Fail closed** (optimise security) | Lock down when integrity is uncertain | Default is deny all |

The two pull against each other. Decide your **minimal non-negotiable security posture**, then make the security-critical parts reliable enough that they do not have to fail open. Security-critical operations should not fail open: a denial-of-service attack alone could then degrade security. Example: tag security RPC traffic for special QoS so it is not dropped.

## Controlling the blast radius

Like ship compartments: constrain both attackers and accidents.

- **Separate by role, location and time**
- **Network segmentation** (VLANs with ACLs) is the classic form; a breach or overload in one compartment does not take down the rest
- Compartments help incident response: freeze and analyse one while recovering another, or jettison a compartment to save the rest
- **Failure domains**: several equivalent, fully independent copies of the system. Each has its own data copy, and updates enter a domain only after validation. This matters for changes such as an ACL generator producing an empty ACL that denies everyone

## Component types

| Type | Role |
| ---- | ---- |
| **High-capacity** | Serve the full feature set to the full user base |
| **High-availability** | Stay up even when high-capacity parts fail |
| **Low-dependency** | Minimal-dependency alternative with limited features, for recovery or temporary load |

A redundant component only helps if it does not share a failure domain with the one it backs up. Low-dependency components cost money and rarely carry normal traffic, so keep the set small.

**Validate** resilience: inject expected failures, and exercise emergency components in normal workflows so they work when needed.

# Recovery

Failures come from four sources: **random** errors (hardware), **accidental** errors (people), **malicious** actions, and **software** errors. Do not spend time classifying edge cases; be ready to recover from all of them.

- **Go as fast as possible, guarded by policy**: the tools that allow fast change can also make the wrong change fast. After a compromise, rushing cleanup can tip off the attacker
- **Know the intended state, down to the bytes**: recovery means returning to a known-good state, so encode the intended state and reduce mutable state per service, host and device. "Stateless" services still have state (code version, port, startup behaviour)
- **Limit dependence on external notions of time** in recovery tooling
- **Block rollback to vulnerable versions**: keep a separate **Security Version Number** that increments with each critical security fix. A **minimum acceptable SVN** is an ordered low-water mark below which systems must never run. It replaces an ever-growing deny list of bad releases

# Safe Deployment

- Require code review, rely on automation, and treat configuration as code
- **Verify artifacts, not just people**: a verified deployer can still make a mistake or push something malicious, so production should check *what* is being deployed. Example: accept only images signed by CI/CD, and watch the audit log for breakglass use
- **Binary provenance**: every build records exactly how an artifact was made, meaning the inputs, the transformation and the entity that built it. Useful fields: authenticity, outputs, input metadata, environment, versioning. In an incident it answers "which source did this deployed binary come from?"
- **Provenance-based deployment policies**: production allows only artifacts whose provenance meets policy
- **Verifiable builds**: a trusted build service, or a rebuild you perform yourself, so the binary matches its source
- **Deployment choke points**: one place every deployment must pass (for example the Kubernetes control node, with workers accepting requests only from it). Policy decisions made elsewhere can be bypassed
- Keep a **deployment breakglass**, and give actionable error messages when policy blocks a change
- Adopt it one step at a time

# Checklist

- Is access classified, and are highly sensitive actions without permanent access?
- Can anyone act as root or admin by default?
- If the ACL or config fails to load, does the system fail open or closed, and was that a decision?
- Is there a smaller, independent fallback for the critical path?
- Is the intended state of every host and service encoded?
- Can an old vulnerable version be rolled back to?
- Does production verify provenance, or only who clicked deploy?
