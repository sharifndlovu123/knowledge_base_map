# 06. Smart Contract Security

The recurring ways contracts and wallets lose funds, and the habits that prevent each.

> **Not from the library.** General reference material. Code is public and value is directly at stake, so mistakes are exploited quickly and cannot be rolled back.

## At a glance

| Weakness | In one line | Defence |
|---|---|---|
| Reentrancy | A callee calls back before state is updated | Checks-effects-interactions, reentrancy guard |
| Access control | Anyone can call a privileged function | Explicit roles, multisig admin |
| Oracle manipulation | A spot price is moved within one transaction | Time-weighted or aggregated feeds |
| Unchecked approvals | Contract pulls more than intended | Minimal allowances, revoke |
| Signature replay | A valid signature is reused | Nonces, chain id, domain separation |
| Front-running (MEV) | Others reorder your pending transaction | Slippage limits, private submission |
| Upgrade/admin risk | A key can change the rules | Timelock, multisig, public process |

## Reentrancy

- An external call hands control to another contract, which can call back into yours **before your function finishes**.
- Bug pattern: send funds first, reduce the balance afterwards. The attacker withdraws repeatedly against the same balance.
- Fixes: update state before the external call (see the vault in [[5. Smart Contracts|Smart Contracts]]), add a `nonReentrant` modifier, and prefer pull payments over pushing value.

## Access control

- Mark every state-changing function and ask "who may call this?".
- Use well-tested role libraries rather than hand-rolled `owner` checks.
- Beware uninitialised proxies and initialisers that anyone can call.
- Keep admin keys in a multisig; treat a single admin EOA as a single point of failure.

## Price oracles and flash loans

- A **flash loan** lends any amount with no collateral if it is repaid in the same transaction, so an attacker can briefly distort a pool's spot price.
- Never use a single pool's instantaneous price as truth. Use aggregated feeds or time-weighted averages, and sanity-check bounds.

## Signatures and approvals

- Off-chain signatures (permits, orders) must bind to **who, what, how much, which chain, which contract and a nonce or expiry**. Use the structured-data standard EIP-712 so wallets can display what is signed.
- For users: signing an opaque "permit" or `setApprovalForAll` can hand over everything. Phishing sites rely on this.
- Review and revoke old approvals with an allowance checker.

## Arithmetic and edge cases

- Solidity 0.8+ checks overflow, but `unchecked` blocks, type casts and rounding errors still bite. Divide last; decide rounding direction in favour of the protocol.
- Mismatched token decimals, fee-on-transfer tokens and tokens that return no value are frequent integration bugs.

## Front-running and MEV

- Pending transactions are public. Searchers may insert their own before and after yours (**sandwich attack**).
- Mitigate with tight slippage, deadlines, commit-reveal schemes or private transaction relays.

## Process that prevents losses

1. Keep contracts small and use audited libraries.
2. Write tests for failure paths, then **fuzz** and add invariant tests (for example "total deposits equals sum of balances").
3. Run static analysis (Slither) and review warnings.
4. Get an independent **audit** for anything holding real value; an audit lowers risk, it does not remove it.
5. Launch with caps, a pause mechanism and monitoring; consider a **bug bounty**.
6. Publish the admin and upgrade process, and use timelocks.
7. Prepare an incident plan before launch: who can pause, who communicates, how to migrate funds.

## Personal security for users

- Phishing is the biggest loss source: fake sites, fake support, fake airdrops, malicious browser extensions.
- Bookmark real sites; do not click links from DMs.
- Use a separate wallet for experiments; never connect your savings wallet to unknown dapps.
- If a key or seed leaks, move funds immediately to a fresh wallet. Compare with the habits in [[3. Keys, Wallets and Signatures|Keys, Wallets and Signatures]].

## Recall

3. Why is a pool's spot price a bad oracle?
4. Does an audit prove a contract is safe?

    1. A reentrant call then sees the already-reduced balance and fails its check.
