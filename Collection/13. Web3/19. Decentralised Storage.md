# 19. Decentralised Storage

How IPFS, Arweave, Filecoin and similar networks store data, what they guarantee, and what they do not.

> **Not from the library.** General reference material written to fill a gap. Network economics and pricing change; check each project's docs.

## At a glance

| Concept | In one line | Use it when |
|---|---|---|
| Content addressing | The name of data is the hash of the data | Verifying integrity without trusting a server |
| IPFS | Peer-to-peer content-addressed file network | Distributing and referencing files |
| Pinning | Asking a node to keep data available | Preventing data from disappearing |
| Arweave | Pay once for long-term storage | NFT metadata and archives |
| Filecoin | Market of storage deals with proofs | Large data with ongoing deals |
| Gateway | HTTP bridge to IPFS | Loading content in a normal browser |

## Content addressing

- Normal URLs say **where** data is; a **CID** (content identifier) says **what** it is.
- A CID encodes a hash (a **multihash**) plus the format. Same bytes, same CID, anywhere.
- Large files are split into **chunks** and arranged as a Merkle DAG; the root CID covers all of it. Change one byte and the root CID changes.
- Benefit: anyone can fetch from any peer and **verify** it against the CID. Content cannot be silently altered.

## IPFS in practice

```bash
ipfs init
ipfs daemon &
ipfs add photo.png                 # prints a CID, e.g. bafy... or Qm...
ipfs pin add <CID>                 # keep it on this node
ipfs cat <CID> > out.png           # fetch by CID
ipfs pin ls
```

How it works:

- Nodes find who has a CID through a **distributed hash table (DHT)** and exchange blocks with **Bitswap**.
- CIDv0 starts with `Qm`; CIDv1 (starting `bafy`) is the modern, case-insensitive-friendly form.
- **IPNS** and DNSLink give a stable, mutable name that points to the latest CID, since the CID itself changes whenever content does.
- A **gateway** (`https://<gateway>/ipfs/<CID>`) lets browsers read IPFS, but the gateway is a trusted intermediary unless you verify the content.

### The most important point

**IPFS does not guarantee persistence.** Data exists only while some node keeps (pins) it. Upload once to one node, shut it down, and the data is gone. Pin on multiple services or nodes, or combine with a storage network that pays for it.

## Persistence layers

| Network | Model | Strength | Caveat |
|---|---|---|---|
| IPFS + pinning services | Pay a provider to keep pins | Easy, flexible | You depend on the provider |
| Arweave | Pay once up front for data meant to be stored long term (check the docs for how the fee is funded) | "Permanent" storage, simple model | Permanence depends on the network's economics holding over a long horizon |
| Filecoin | Storage deals with providers who prove they hold your data | Large scale, proof-based | Deals have terms; you must renew or manage them |
| Storj, Sia, and similar | Encrypted shards on rented nodes | Cloud-like cost model | Network-specific |

**Filecoin proofs**: providers submit **proof-of-replication** (a unique copy is stored) and **proof-of-spacetime** (it is kept over time), and are penalised for failures.

## Using storage with smart contracts

- Storing bytes on-chain is very expensive, so contracts store a **hash or URI** and the data lives elsewhere.
- NFT `tokenURI` should point at `ipfs://<CID>/metadata.json` or an Arweave id, not a plain company web server that can disappear or change.
- Include media inside the metadata by CID so both are content-addressed.
- If the contract stores only the **hash**, anyone can verify downloaded data against it, even from an untrusted source.
- For mutable data, store a new CID on-chain per update and emit an event, rather than overwriting history.

```json
{
  "name": "Example #1",
  "description": "Metadata stored by content address",
  "image": "ipfs://bafy.../1.png"
}
```

## Querying data: indexers

- Chains are poor at queries. Indexers such as **The Graph** subgraphs read events and store them in a queryable database exposed through GraphQL.
- Verify that important results are consistent with on-chain data, and handle chain reorganisations.
- See [[7. Web3 Development Workflow|Web3 Development Workflow]].

## Security considerations

- **Public by default**: anything uploaded is readable by anyone with the CID. **Encrypt before upload** for sensitive data and manage keys separately.
- **No deletion**: you can unpin your copy but cannot force others to forget. Do not publish anything you may need to remove.
- **Link rot and pin loss**: unpinned CIDs disappear; monitor and re-pin.
- **Gateway trust**: a malicious gateway could serve wrong bytes; verify the hash, use a trusted gateway, or run your own node.
- **Mutable pointers**: IPNS and DNSLink can be repointed by their key or DNS owner; protect those.
- **Phishing and malicious content**: a valid CID can still contain malware or scripts; sandbox content in dapps and sanitise rendered files such as SVG or HTML.
- **Metadata rug-pulls**: if an NFT's URI is a changeable web server, the owner can swap the image. Prefer immutable CIDs and "freeze" metadata on-chain.
- **Privacy leaks**: DHT lookups and peer connections can reveal which CIDs you request.

## Choosing

| Need | Option |
|---|---|
| Quick dapp assets with moderate durability | IPFS with two or more pinning providers |
| Long-term archival of small, important data | Arweave |
| Large datasets with contractual guarantees | Filecoin deals |
| Private data | Encrypt first, then any network |
| Query history of on-chain events | Indexer (subgraph or own database) |

## Common mistakes

- Treating "on IPFS" as "permanent".
- Using an HTTP gateway URL in the contract instead of the `ipfs://` form.
- Uploading unencrypted personal data.
- Storing large files on-chain.
- Forgetting that changing a file changes its CID, breaking references.

## Recall

1. What does a CID identify?
2. Why can an IPFS file vanish?
3. What should an NFT `tokenURI` point at?
4. Why encrypt before uploading?

??? note "Answers"
    1. The content itself, via its hash, rather than a location.
    2. Nodes keep it only while they pin it; if all pins stop, it is gone.
    3. An immutable content address such as `ipfs://<CID>` or an Arweave id, not a mutable web server.
    4. Everything uploaded is public and cannot be reliably deleted.
